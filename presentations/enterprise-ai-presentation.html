04 / 30效率方法 / 把经验写成能力
效率方法 / 把经验沉淀下来

不要重复解释，
把经验沉淀成 可复用的 Skill。

一条成功路径只有被记录、验证、迭代，才会从个人技巧变成团队能力。

01 / 收集素材

从真实对话开始

汇总 Chat History、经验总结和失败案例，保留输入、判断、修改与最终结果。

02 / 抽取规律

找出稳定的任务模式

明确任务目标、必要输入、判断标准、输出格式，以及哪些情况不能自动处理。

03 / 写成规范

把流程写成可执行步骤

写清触发条件、执行顺序、工具权限、边界条件和需要人工确认的节点。

04 / 持续评估

用失败案例迭代

用代表性案例做 Eval，记录失败原因、修复方式和版本变化，避免问题重复发生。

Skill 最少要写清楚

让使用者知道什么时候调用，也让系统知道什么时候停下来。

  • 触发条件 / 什么时候使用
  • 输入与步骤 / 需要什么、怎么做
  • 输出与验收 / 交付什么、怎样算合格
  • 边界与回退 / 不能做什么、何时找人
关键判断：失败案例不是附录，而是 Skill 最有价值的部分。它告诉我们模型会在哪里误判，以及流程需要增加什么约束。
05 / 30落地方法 / Context first
落地方法 / 先理解上下文

Skill 不是孤立的 Prompt，
它必须嵌入 真实企业流程。

判断标准 / CONTEXT FIRST
同一个 Skill，
换一个企业，
结果可能完全不同。

目标、角色、数据、权限、系统和责任边界变了，Skill 的输入、输出和风险也会跟着变化。

01 / 业务目标

要改善什么指标？

节省时间、降低成本，还是提升质量与收入？

02 / 使用角色

谁使用、谁负责？

明确使用者、最终判断人和结果验收人。

03 / 数据权限

模型可以看到什么？

定义数据边界、脱敏要求和可调用的系统权限。

04 / 工作流程

输出接下来去哪？

明确交接系统、后续动作和异常处理路径。

05 / 风险标准

什么时候必须停下？

设定人工审核、准确率、延迟与合规要求。

落地方法先画流程 → 再拆任务 → 小范围 POC → 用真实指标 Eval → 明确责任与迭代

09 / 30企业 AI / 不要给旧流程贴补丁
流程方法 / AI 原生工作

AI 的价值上限，
常常由 流程重构 决定。

如果只是把 AI 接到旧流程上，效率提升会被冗余、等待和重复审批重新吃掉。

常见做法 / PATCH THE OLD

在旧流程上叠加 AI

  • 目标让某个岗位更快完成一个任务
  • 流程输入、审批、交接和系统边界保持不变
  • 结果局部效率变高，整体周期和成本不变
  • 风险AI 变成新的孤岛，越用越复杂
推荐做法 / REDESIGN THE WORK

围绕目标重写工作

  • 目标先定义要改善的业务指标
  • 流程删除冗余、合并重复，重新划分人机分工
  • 结果让时间、质量或收入真正进入经营结果
  • 边界人保留判断、决策、创新和异常处理
三个重构问题：哪些环节可以消失？哪些任务可以交给 AI？人只保留哪些高价值判断？
观点来源：方跃《企业AI转型：如何从“表演”走向价值》，中欧国际工商学院
10 / 30企业 AI / 七步价值闭环
落地方法 / 从试点走向价值

每个 AI 项目，
都要走完一条 价值闭环。

01

锚定价值

只选择一个核心业务目标，并由业务负责人验收。

02

重构流程

删除冗余，明确人机分工，不给旧流程贴补丁。

03

建立核算

上线前估算，上线后实测，规模化后纳入经营分析。

04

小步试点

先在最小业务单元验证，稳定后再逐步放量。

05

标准化

把模型、数据、流程、权限和运维做成可复制组件。

06

人机协同

AI 增强判断与创造，不把员工只当成可替代成本。

07

及时叫停

达不到价值、无法复制或只适合演示，就停止投入。

生产标准：可衡量、可复制、可规模化；否则只是 Demo，不是企业能力。

11 / 3002 / 企业 AI 落地的典型误区
误区一 / 不要把岗位当成一个任务

AI 会替代一部分工作，不等于一键替代一个人。

01
最容易出现的误判

以为 AI 很快就可以取代人

误区

模型能力增长很快，于是从“AI 能做一部分工作”，直接跳到“这个岗位是不是可以不要了”。

现实

真正落地时，岗位背后还有任务拆解、流程、数据、权限、验收、责任和异常处理。

先替代什么？一个岗位里可拆开、可标准化、可验收的部分任务。
先替代任务，再重构岗位。
12 / 3002 / 企业 AI 落地的典型误区
误区二 / 看起来会回答，不等于能交付

做出一个 ChatGPT Demo，
离完成还很远。

02
Demo 只证明一件事

某一次输入，得到了一个不错的答案

Demo 解决的是

AI 能不能给出一个看起来不错的答案？

生产要解决的是

真实输入进来以后，能不能稳定、重复、可验收地交付？

差距在这里输入格式、缺失信息、失败分支、输出格式，以及谁来验收。
一次漂亮回答，不等于一条可靠流程。
13 / 3002 / 企业 AI 落地的典型误区
误区三 / 速度放大了，责任没有消失

Codex 跑出了 Demo，
不代表系统可以稳定上线。

03
AI Coding 的错觉

代码生成快，生产系统就会快

开发阶段

很快得到能跑的代码和可演示的路径，适合验证想法与拿到反馈。

上线之后

测试、边界、监控、权限、异常处理、数据一致性、回滚和长期维护都要补齐。

生产化清单可观测、可回滚、可追责；出了问题，系统知道如何停下来。
Demo 能跑，是开始，不是结束。
14 / 3002 / 企业 AI 落地的典型误区
误区四 / 像人一样说话，不等于一定是真的

不要把核心判断，
直接外包给 LLM。

04
幻觉的真实风险

输出很像人，事实却可能不成立

高风险内容

事实、数字、权限、法律、财务和业务规则，都不能只靠模型输出。

合理边界

AI 可以承担重复方法，但高风险判断、最终责任和授权边界仍然需要人。

先定义边界什么可以自动做，什么必须核验，什么情况下必须停下来交给人。
让 AI 承担方法，让人保留责任。
15 / 3002 / 企业 AI 落地的典型误区
误区五 / 另一个极端同样危险

很多“做不到”，其实是任务没有拆对。

05
不是模型不行

而是把一个太大的任务直接扔给 AI

常见卡点

输入缺失、任务过大、模式不匹配、模型不适合，或者验收标准模糊。

重新拆解

把复杂任务拆成目标、子任务、输入、规则、输出和验收，再逐步验证。

失败通常说明问题没有拆对，流程没有设计好，场景没有选好，结果也没有被清晰定义。
先把问题变小，再把能力做大。
16 / 30AI 落地的基础
总结 / AI 不是即插即用

AI 不是又一个功能，
而是一项企业能力。

AI 能力只是可见的 10%；真正驱动价值的，是水面下的企业准备度。

落地底座

可靠数据、可扩展基础设施、治理、安全、有效模型与专业人才。

主要障碍

数据质量不足与组织准备度不够，往往比模型本身更先卡住项目。

企业架构

把 AI 对齐业务目标、技术现状与目标运营模型，避免孤立建设。

变革管理

推动采用、建立信任，让新能力真正进入日常工作。

AI 不是技术项目，而是一段企业转型旅程。

17 / 30AI 落地的三层冰山
进一步拆开 / 企业 AI 冰山

用户看到的只是展示层，
真正的工作在水面之下。

AI 看起来很小，直到真实用户开始点击。规模化依赖的不只是模型，而是完整的工程、治理与运营体系。

展示层

Dashboard、Copilot、Chatbot、报告，是大家最先看到的 10%。

工程层

数据管道、RAG、身份管理与评测系统，支撑真实任务稳定运行。

治理与风险

治理模型、风险框架、合规映射，定义谁负责、如何审批与如何追溯。

运营与责任

运营模型与责任模型，让 AI 能持续部署、监控、改进并扩大。

展示层带来注意力，水面下的系统决定能否成功。

× 优化流程

适合✓ 质检 / 巡检
✓ 数据录入 · 报告生成
避开× 一次性决策
× 高度个性化场景

21 / 30AI、Workflow 还是程序
一个场景不要整包交给 LLM

每一步选择最合适的能力。

固定规则

固定流程

真实业务通常是：程序 + Workflow + LLM + 人。预测型 AI 也不要默认用 LLM。

27 / 30企业 AI 落地行动路线
回去以后具体做什么 / 价值优先

从一个业务目标开始，
走完验证、复制与止损。

01 / VALUE

只定一个目标

明确痛点、业务负责人和可量化的成功指标。

02 / PILOT

最小单元试点

用真实材料跑通工作流，记录结果和失败证据。

03 / SCALE

标准化再放量

把模型、数据、流程、权限和运维做成可复制组件。

04 / STOP

不行就及时叫停

价值不成立、无法复制或只适合演示，就停止投入。

继续的条件：价值可衡量、流程可交付、方案可复制。
停止的条件：没有业务价值，或规模化成本超过收益。
行动框架参考：方跃《企业AI转型：如何从“表演”走向价值》，中欧国际工商学院

29 / 30带走五个判断
总结 / 从工具到工作重构

AI 落地不是多买一个工具，
而是重新设计工作。

先从一个真实场景开始。
用可验收的标准跑通一次。
再把结果复制到更多工作。
01 / 从真实工作开始

不要从 AI 能做什么开始，从公司每天在做什么开始。

02 / 先设计问题

许多失败来自问题、流程和验收没有设计好。

03 / 看完整成本

Token 不是全部成本，人、数据、流程和组织同样重要。

04 / 区分 POC 与生产

POC 成功不是上线成功，上线才是持续反馈的开始。

30 / 30模型策略：先稳定行为，再考虑微调
什么时候考虑微调 / 不要把微调当成第一步

微调不是为了让模型知道更多，
而是让它在稳定任务上做得更一致。

01 / 任务稳定

重复量大、输入输出相对固定

适合分类、信息抽取、审核、格式转换等长期运行的同类任务。

02 / 样本充足

已经积累高质量示例

有经过人工验收的输入 / 输出样本，并覆盖常见情况和边界情况。

03 / 行为稳定

需要固定风格和输出格式

希望模型稳定遵循术语、语气、字段结构或业务模板，Prompt 仍然不够稳定。

04 / 成本优化

调用量大，成本或延迟需要下降

用更小的微调模型减少上下文、降低单次成本，或提升响应速度。

先别微调：知识需要持续更新 → RAG；事实和权限实时变化 → 工具调用；没有高质量样本 → 先做数据积累和 Eval；偶尔使用 → 很难摊平微调成本。
知识要更新 → RAG；行为要稳定 → 微调；数据要实时 → 工具调用；流程要可靠 → Workflow + Eval。
