12 / 44Skill Best Practise
触发之前，模型只看到元数据

Skill Best Practise：先被正确发现，
再被正确执行。

  • 保持简洁。删掉模型已经知道的常识；每一段都要值得占用上下文。
  • 匹配自由度。启发式任务给高自由度；有固定模式用模板；脆弱操作给精确步骤。
  • 做好元数据。启动时预加载 name + description；它们决定 Skill 是否会被发现和触发。
  • 让内容可维护。引用走一层、文件名描述性强；旧方法单独归档，避免主流程过时。
  • 使用渐进式披露。主 SKILL.md 保持精简，完整细节放到按需加载的参考文件。
  • 统一术语与示例。同一个概念只用一个称呼，示例要具体；同时给出一个默认路径，不要罗列过多选项。
# discoverability metadata name: analyzing-sales description: Analyzes sales data and builds reports. Use when users ask for revenue, pipeline, or performance analysis.
读取顺序：
启动时：预加载 name + description
触发后：读取 SKILL.md
按需：读取 reference/ 等文件

写作原则：description 写能力 + 触发场景；步骤、边界和验收放进 SKILL.md。
13 / 44Skill Best Practise
把质量变成可观察的反馈

真正的质量来自测试、验证与持续迭代。

  • 复杂任务写工作流。用清晰、连续的步骤和 checklist，降低漏步骤的概率。
  • 建立反馈闭环。执行验证 → 修复问题 → 再次验证，直到验收通过。
  • 给关键操作设停止条件。高风险、破坏性或不可逆动作，先生成计划再执行。
  • 产出可验证的中间结果。批量修改、表单填充等任务先生成计划文件，再校验、执行、复核。
  • 脚本要解决问题。显式处理错误，解释关键参数，列出依赖；不要把难题丢回给模型。
  • 确定性操作优先用工具。能直接运行的 utility script，比每次临时生成代码更可靠。
  • 先做评估再写长文档。至少准备三个场景，先建立无 Skill 基线，再测试不同模型与真实任务。
  • 观察真实使用行为。关注漏读引用、反复探索、被忽略的内容，并吸收团队反馈持续改版。
不要凭感觉写说明书，用真实使用行为观察 → 修正 → 再测试。
14 / 44Spec-Driven Development
把意图写成可验证的契约

Spec 不是实现计划，
而是可验收的任务契约。

Spec 写什么 / WHAT

  • 为什么做：背景、目标、用户价值。
  • 改哪里：范围、边界、明确不做什么。
  • 要做到什么：行为、输入输出、错误和不变量。
  • 怎么判断完成：场景、验收标准和验证方式。

Plan 写什么 / HOW

  • 选择哪些模块、文件和技术方案。
  • 怎样拆任务、安排顺序和分配责任。
  • 怎样落地实现、迁移、回滚和发布。
  • 这些决定应基于仓库现状，而不是写死在 Spec 里。
写下不能靠猜的决定，把可以从仓库发现的决定留给 Agent。
15 / 44Spec-Driven Development
足够严格，也足够容易维护

一份够用的 Feature Spec，
先把“什么必须为真”写清楚。

# specs/account-deletion.md # Feature: Account deletion ## Intent 删除账号后不再拥有有效会话。 ## Scope - In: deletion and active sessions - Out: registration and billing history ## Requirement - 删除后，所有 active sessions 立即失效。 ## Scenario Given active sessions → When deleted → Then reject ## Acceptance - [ ] Existing sessions cannot authenticate - [ ] Registration flow is unchanged
WHAT：所有 active sessions 必须立即失效。

HOW：是否新增 revokeSessions()、放在哪个 Service、使用什么存储，由 Agent 先检查仓库再提出 Plan。

关系：Spec → Acceptance Criteria → Tests。测试是可执行的验证，不是 Spec 本身。
16 / 44Spec-Driven Development
大项目不要写一份巨型 SPEC

把复杂目标拆成阶段、局部文件和可验证结果。

01Intent为什么做
02Specify写清契约
03Clarify解决歧义
04Plan决定如何做
05Tasks拆成任务
06Implement分阶段实现
07Validate对照契约验收
project/ ├── AGENTS.md ├── specs/ │ ├── product.md │ ├── architecture.md │ ├── auth/ │ │ └── auth.md │ └── billing/ │ ├── billing.md │ └── invoice.md └── src/ ├── auth/ └── billing/
  • AGENTS.md 放项目级规则；product.md 与 architecture.md 放稳定的全局上下文。
  • 领域 Spec 放在 specs/auth/、specs/billing/，靠近对应的业务边界。
  • Agent 一次只加载当前阶段、当前领域需要的文件，避免巨型上下文。
  • 大型重构先切边界，再切迁移批次；不要一次改完整个系统。
17 / 44Spec-Driven Development
让 Agent 按阶段推进，而不是一次性冲刺

用 /goal 把 Spec 变成有状态的执行循环。

# 示例：把目标、范围和验证一起交给 /goal /goal 读取 specs/checkout/ 按 Phase 1 → Phase 3 执行 每个 Phase：Plan → Implement → Validate 完成后汇报证据和剩余风险 遇到范围或契约不清：先暂停提问
  • 指定入口：给出 Spec 文件或目录，不让 Agent 自己猜上下文。
  • 指定阶段：一次推进一个 Phase，完成验证后再继续。
  • 指定状态：每阶段记录完成项、证据、风险和下一步。
  • 指定停止条件：边界、权限、数据契约不清时先停，不要擅自扩大范围。
/goal 不是替代 Spec 的魔法命令；它的价值是让目标、阶段、验证和停止条件持续可见。
18 / 44Agent loop / 新功能开发
把一次交付变成可观察的迭代

新功能不是“一次生成”，
而是目标驱动的行动闭环。

01 / GOAL明确目标读取 Spec，确认范围、验收和停止条件。
02 / EXPLORE探索仓库搜索符号、依赖和现有测试，只取相关上下文。
03 / PLAN提出计划拆成小步骤，先让人确认高风险决定。
04 / IMPLEMENT执行修改按阶段编辑代码，每次变更保持可回退。
05 / VERIFY验证证据运行测试、检查 diff，对照 Acceptance Criteria。
06 / NEXT完成或继续满足条件就停止；失败则带着证据进入下一轮。
核心：每一轮都回答“当前状态是什么、下一步为什么做、什么证据可以停止”。
19 / 44Agent loop / 一次迭代
让每一步都能复盘

以“订单导出”为例：
Agent 通过证据 → 决策 → 验证推进。

# iteration 03: implement export endpoint goal: add order export state: API contract clarified read: orders/service.ts, orders.test.ts plan: add CSV serializer + endpoint test edit: 2 files changed run: npm test -- orders evidence: 18 passed, diff reviewed decision: continue → add permission case
  • 进入：Spec 已明确输入、输出、权限和验收标准。
  • 行动：先搜索相关符号和测试，不读取整个仓库。
  • 反馈：工具结果只保留失败、差异和下一步需要的证据。
  • 停止：功能验收通过，或遇到契约、权限、数据风险时暂停。
INPUT目标与上下文Spec + 当前状态
ACTION工具与修改一次小步
FEEDBACK结果与证据测试 / diff / 日志
DECISION继续或停止遵守边界
20 / 44Token Engineering
先看总账，再优化句子

Token 成本不只来自 Prompt，
更来自重复上下文 × Agent 循环次数。

Input tokens

系统指令、历史对话、工具 Schema、代码、RAG 结果。

重复发送 = 隐性成本
Output tokens

回答、推理、工具参数和失败后的重试内容。

max_output_tokens
Number of calls

一次分类、提取、总结、格式化，是否真的需要四次调用？

少循环，少重试
Total cost ≈ input tokens × input price + output tokens × output price × number of calls
优先级：Prompt caching → context compaction → tool filtering → model routing → loop / call reduction。
21 / 44Token Engineering / Coding Agent
你控制不了全部循环，就先控制进入上下文的内容

Codex / Claude Code：先压缩工具输出。

RTK 的位置

Agent runs shell command
　　　 ↓ hook rewrites
RTK executes the real CLI
　　　 ↓ filter / summarize / dedupe
compact output
　　　 ↓
LLM context

它不改变模型，只改变 Shell 输出进入上下文的形状：单个 Rust binary、100+ 命令、低开销。

为什么会变短

Smart filtering：去掉注释、空白、模板和进度噪声。

Grouping：按文件、目录、规则或错误类型聚合。

Truncation：保留关键上下文，截掉重复长行。

Deduplication：重复日志折叠为一条并附出现次数；测试通常只保留失败项。

边界要说清：RTK 官方称最多可减少 90% 的 Bash 输出，但这不等于账单减少 90%。它只控制输入 Token 的一个来源；rtk gain 用 bytes / 4 估算 Token，百分比有意义，绝对值不是供应商账单。 官方仓库
22 / 44Token Engineering / Own Agent
自建 Agent 可以控制整个循环

把 RTK 的思想升级为Token-aware Tool Middleware。

01 / TOOL OUTPUT压缩结果truncate、summarize、deduplicate，只返回对下一步有用的信息。
02 / CONTEXT按需取证RAG top 3–5、摘要旧历史、缓存稳定前缀和结果。
03 / SCHEMA筛选工具按任务暴露工具组，减少无关 Schema 和错误调用。
04 / MODEL任务路由简单分类用小模型，复杂规划和编码用强模型。
05 / LOOP控制循环并行调用、限制重试、设置 max turns 和明确终止条件。
Tool → raw result → token optimizer → diff / cache / structured extraction → agent context
两种场景的差别：Codex / Claude Code 主要让工具返回更少；自建 Agent 还可以决定“何时取、取什么、调用几次、何时停止”。

27 / 44从 Prompt Engineering 到 Graph Engineering

31 / 44LLM 幻觉：原因与解决
生成合理，不等于事实正确

LLM 会“编造”，不是因为它想撒谎。
而是生成 ≠ 验证。

为什么会发生

概率生成

模型优先生成“像答案”的文本，不会自动为事实背书。

上下文缺失

没有企业规则、真实数据或最新资料，只能依赖已有模式。

边界模糊

问题太大、输入不完整、验收不清，模型容易补齐不存在的信息。

怎么解决

给它依据

接入文档、数据库、工具和可追溯来源，不让它凭空回答。

让它可验收

要求引用、结构化输出、测试、规则检查和失败证据。

保留人审

事实、数字、权限、法律、财务和业务规则不直接外包。

高风险判断不能只问“像不像答案”，要问：依据是什么？如何验证？谁负责？

参考：3 key product development loops31

33 / 44RAG：蒸馏层
RAG 的质量，在检索之前就决定了

先修复知识单元，
再去调向量检索。

蒸馏层在向量化前，把文档变成更小、更干净、带治理信息的问答知识单元。
  • Chunk 是被忽略的前提。按 token 切出的文本没有想法边界、版本上下文或权限状态，检索容易返回不完整或互相冲突的证据。
  • 用问答包替代文本窗口。一条经过验证的事实，加上类型化治理字段，让索引单元匹配用户真实的提问方式。
  • 在向量化前做蒸馏。在所给基准中，语义去重最多将语料缩小 40 倍，查询 Token 减少 3 倍，检索距离改善约 2.3 倍。
  • 让治理字段随数据走。版本、密级、隐私和来源元数据跟随每个知识块，而不是依赖脆弱的编排层逻辑。
  • 七个阶段让故障可定位。范围定义、摄取、抽取、去重、自动打标、专家校验，最后导出到向量库。
实践规则：先在上游清理并结构化知识单元，再让检索、重排和 Embedding 专注于匹配。

35 / 44Agentic Design Patterns / 决策树
模式选择，从任务开始

根据任务属性选择模式。
不要先从架构开始。

根据任务属性选择 Agent 设计模式的决策树。
  • 1. 先看路径是否已知。如果流程确定且可预测，使用顺序工作流；只在需要理解或生成的地方调用模型。
  • 2. 按需增加能力。开放式任务需要工具和外部信息，接入 API、数据库、文档和系统操作。
  • 3. 区分规划与探索。阶段和依赖关系清晰时使用 Planning；结构在执行中逐渐形成时使用 ReAct。
  • 4. 有意识地为质量付费。质量标准明确、错误成本足够高时，再增加 Reflection 和额外延迟。
  • 5. 只为真实瓶颈扩展。只有专业化或规模问题确实存在时才使用 Multi-Agent，否则单 Agent 通常已经足够。
模式是起点。随着反馈、约束和失败信号积累，持续重新评估。
36 / 44Agentic Design Patterns / 框架
模式 = 能力与执行形态的组合

用两种视角定位模式：
Agent 做什么，以及工作如何流动。

Agent 设计模式框架：认知功能 × 执行拓扑。
  • 纵向看认知功能。感知、记忆、推理、行动、反思、协作和治理，描述 Agent 正在完成什么工作。
  • 横向看执行拓扑。链式、路由、并行、循环、层级和编排，描述工作与控制如何流动。
  • 模式是可组合的积木。例如 RAG Pipeline、Tool Dispatch、Plan-and-Execute、Fan-Out / Gather 和 Hierarchical Delegation。
  • 跨切面能力保证可运营。Observability、Evaluation & Validation、Security & Identity 贯穿整个矩阵。
  • 设计含义：先定位所需能力和拓扑，再组合解决任务所需的最小模式集合。
决策树负责选择起点，矩阵负责展示如何组合。

40 / 44AI 时代的开发者能力
AI 越强，人的稀缺价值越集中在判断

代码会越来越便宜，
但判断会越来越贵。

01 / 需求建模（链接物理世界）

把现实目标变成可执行契约

把真实业务、用户场景、范围和验收条件讲清楚。输入越含糊，Agent 越容易快速放大错误方向。

02 / 架构裁量

用约束缩小可选空间

把模块边界、数据不变量和架构原则写成 Agent 能执行的规则，把长期经验沉淀为可复用约束。

03 / 质量担责（链接物理世界）

用证据守住真实后果

让测试、评审、发布门禁、线上观测和用户反馈形成证据链。代码可以由 AI 生成，质量风险仍需要人来承担。

投入要按风险分配：标准化、低风险的小团队项目可以少做架构仪式；复杂系统、关键数据和长期演进仍需要明确约束。AI 会接管越来越多的架构实现，但不会自动替你承担后果。
41 / 44Multi-Agent / Distributed Systems
不要把多个 Agent 只设计成群聊

多个 Agent 如何通信？
先把它当成分布式系统。

# task and message flow User Goal │ ▼ [Router / Manager] ┌─┼──────────┐ ▼ ▼ ▼ Planner Researcher Coder └────┬─────┘ ▼ [State / Event Log] ▼ [Reviewer] pass / retry / stop
  • 消息契约：task_id、sender、recipient、type、payload、evidence。
  • 状态所有权：一个 Agent 负责写入，其他 Agent 提交建议或只读。
  • 失败边界：超时、重试、重复消息、背压和权限都要显式处理。
  • 终止与观测：定义 DONE 条件，并记录消息、决策、工具、Token。
通信模式结构适合场景主要风险
Point-to-PointAgent A → Agent B明确的任务交接强耦合、单点依赖
Broadcast / Group Chat一条消息 → 多个 Agent共享上下文、多人评审上下文膨胀、重复响应
Broker / Event BusAgent → Broker → Agent事件驱动、异步协作消息顺序、重复消费
Shared StateAgent ↔ State Store长流程、可恢复任务状态竞争、权限混乱
判断标准：先决定谁能看到消息、谁能修改状态、谁有权继续，再决定通信拓扑。
42 / 44Multi-Agent / AutoGen
Runtime 把参与者、路由和终止条件放在一起管理

AutoGen：把 Agent 协作变成可管理的消息系统。

# AutoGen: message-oriented team Task │ ▼ [Team / Manager] ┌──┼─────────┐ ▼ ▼ ▼ Planner Researcher Reviewer └──┬────┘ ▼ Runtime topics + tools ▼ termination condition
  • 参与者：用 AssistantAgent 表示不同角色，按职责接收任务或输出证据。
  • 消息路由：Team / Manager 将消息发布给参与者；参与者共享必要上下文，但不共享所有内部状态。
  • 工具边界：通过 FunctionTool、AgentTool 或 MCP 暴露能力，工具仍需权限、超时和幂等控制。
  • 停止条件：TerminationCondition、最大轮次和人工介入共同防止无限协作。
message = { task_id, sender, recipient, type, payload, evidence, created_at }
trace = run → participant message → tool call → result → next decision → termination
分布式映射：Agent 是服务角色，Team / Manager 是路由层，Runtime topic 是消息地址，termination 是系统停止条件。 AutoGen 官方仓库
AutoGen 当前处于 maintenance mode；这里把它作为多 Agent Runtime 的通信示例，新项目也应评估 Microsoft Agent Framework。
