03 / 092026 status check
MAF and LangGraph are current orchestration choices

Which orchestration layer?
Choose by operating model.

Microsoft Agent Framework / MAF

Best fit for Microsoft-aligned production workflows.

MAF is Microsoft's current open framework for production agents and multi-agent workflows across Python, .NET and Go.

  • Native graph workflows: sequential, concurrent, handoff and group collaboration.
  • Checkpointing, streaming, time-travel and human-in-the-loop support.
  • OpenTelemetry, middleware, declarative agents and Agent Skills are part of the current platform story.
Decision: choose for Microsoft ecosystem, governance and multi-agent workflow depth.
Source: Microsoft Agent Framework repository
LangGraph / official positioning

Relevant when state is the product.

LangGraph is positioned as a low-level orchestration framework for long-running, stateful agents. Keep provider and tool integrations behind adapters that fit your system.

  • Use it for explicit state, branching, durable execution, human review and restartable workflows.
  • Its graph model is a good base for controlled handoffs and multi-agent workflows.
  • Keep gateway, tenant and delivery ownership outside the graph unless you intentionally choose a hosted platform.
Decision: a credible 2026 orchestration layer, not a complete product gateway.
Source: LangGraph overview

Agno is the more bundled platform alternative: SDK + AgentOS runtime + UI, with JWT-based RBAC, OTel tracing, cron scheduling, audit logs and human approval in its official feature set. Source: Agno repository

04 / 09Self-build solution
Capability comes packaged; product responsibility does not

Self-build SDKs are strong workers.
You still own the system around them.

OpenAI / Codex SDK

Programmatic control for coding-focused Codex threads.

OpenAI positions the SDK for controlling local Codex agents. When Codex is one specialist inside a broader workflow, its docs point to MCP and the Agents SDK for orchestration around it.

  • Use it as a coding worker for repository tasks, workspace edits and engineering loops.
  • Good fit when Codex capability is the differentiator and the product team wants its own UX.
  • You still build gateway, auth, tenant isolation, approvals, event schema, delivery and evaluation.
Decision: strong worker primitive; not a product control plane.
Source: OpenAI Codex SDK
Anthropic / Claude Agent SDK

Claude Code capabilities as a programmable agent library.

Anthropic's current docs call it the Agent SDK. It exposes the tools, subagents, MCP connections, permissions and context management that power Claude Code in Python and TypeScript.

  • Use it when a Claude Code style coding agent is the core worker inside a custom application.
  • Good fit for custom orchestration, approval UX and product-specific policy.
  • You own the same outer system concerns: gateway, tenancy, budgets, audit, delivery and regression evaluation.
Decision: strong coding-agent building block; still a self-build product.
Source: Claude Agent SDK overview
Composition rule: add LangGraph when durable state and branching are the hard part; add a Codex or Claude SDK when the coding worker is the hard part. Neither SDK removes the need for a worker contract.

Keep the current production line intact while testing the next one

One production path.
One shadow path.

Hermes → DSH

Hermes owns channels, sessions, policy and delivery. DSH owns coding, workspace and trajectory.

Recommended production
02 / GREENFIELD

OpenClaw + Pi

OpenClaw provides the gateway; Pi supplies the thin runtime. The split is light, but permissions, tenant policy, audit and quotas still need to be built.

Recommended shadow
03 / CONDITIONAL

OpenClaw + DSH

Higher coding ceiling, heavier adapter and lifecycle ownership. Choose only after a worker benchmark proves the gain.

Benchmark first

DSH alone

Most consistent runtime story, but it also becomes UI, gateway, auth, tenant and delivery platform.

Not the first move
LangGraph, MAF, Agno and self-build SDKs sit inside this map as runtime choices. None of them removes the need to name the gateway owner, worker owner or delivery owner.
07 / 09Migration boundary
Do not bind gateway migration to runtime migration

Define one contract.
Let the worker change behind it.

Contract fields

  • Task passport
    tenant / user / project / workspace / task
  • Worker events
    start / progress / tool / approval / done
  • Policy owner
    gateway or sidecar; worker never bypasses it
  • Session owner
    child runtime manages its own local state
  • Delivery owner
    gateway sends the final message and files
  • Evaluation fields
    latency / cost / success / trajectory / retries
# same passport, different runtime task = { "tenant_id": tenant, "workspace": workspace, "task_id": task_id, "worker": "dsh | pi | codex | claude | langgraph | maf" } event = { "type": "tool | approval | done", "evidence": evidence, "next": next_action }
Why it matters: the same contract can connect Hermes-native, DSH, Pi/OpenClaw+Pi, OpenClaw+DSH, LangGraph, MAF, Codex SDK or Claude Agent SDK without moving the gateway, tenant model and delivery system together.
